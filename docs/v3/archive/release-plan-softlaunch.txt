Status: Launch preparation

1. Executive decision

Solaris Studio V3 will no longer wait for every planned feature to reach completion before opening to the public.

Instead, Solaris Studio will launch with a smaller set of fully functional, verified features.

All unfinished features will remain hidden or restricted until individually verified and authorized for release.

The November 14 launch must deliver:

1. A functional, polished Solaris Studio homepage.
2. Working authentication and user permissions.
3. Working country confirmations.
4. Working jury voting.
5. Working televoting.
6. Working Organizer controls for every enabled contest workflow.
7. Essential participant information, deadlines, status and submission receipts.
8. Any additional public features that independently pass the release requirements.

The release must preserve existing Solaris contest data, security, canonical authority and publication rules.

The launch date is a target, not permission to bypass integrity or security requirements.

2. Initial launch scope

2.1 Required public features

Capability	Required outcome
Home	Complete, polished, current contest information
Authentication	Secure sign-in, account/session handling
Confirmations	View, submit, edit when permitted, receive confirmation
Jury	Open eligible ballot, save draft, submit, receive receipt
Televoting	Vote in eligible round, submit once according to rules, receive receipt
Participate	Display available actions, deadlines and status
Me	Essential account, delegation and submission information
Explore	Minimum verified country/edition discovery
Search	Verified public destinations only
Rules	Accessible current official contest rules and voting instructions

The five canonical public navigation areas remain Home · Explore · Participate · Results · Me.

They may initially provide reduced functionality, but must not contain broken links, misleading controls or fabricated data.

2.2 Conditional public features

These can be added to the November 14 release only if already integrated, verified and publication-safe:

* Country and edition profiles.
* Published historical results and scorecharts.
* Current edition schedule.
* Official announcements.
* Entry and artist information.
* Notifications.
* Live Show information.

Results publication must not be enabled merely because the Results page renders. Official publication and correction workflows require independent verification.

2.3 Deferred features

Keep these unavailable in the initial release unless independently certified:

* Fantasy SSC.
* Prediction League.
* Voting DNA and advanced analytics.
* Time Machine.
* Experimental Labs.
* Advanced historical/archive tools.
* Full Terra Solaris World and institutional governance.
* Unfinished community, personalization and specialist experiences.
* Other unverified V3 capabilities.

Do not delete their implementation.

Continue development separately and enable them incrementally after launch.

3. Required Organizer system

Organizer functionality is a prerequisite for activating the corresponding public feature.

3.1 Confirmation management

Organizers must be able to:

* Open and close confirmation rounds.
* Configure eligible delegations and requirements.
* Monitor responses.
* Review confirmation statuses.
* Perform approved waive/reconfirm operations.
* Extend or reopen deadlines when permitted.
* Inspect records and recover uncertain operations.

All changes must use the canonical Confirmation authority.

3.2 Jury management

Organizers must be able to:

* Configure jury rounds and eligible voters.
* Open and close rounds.
* Monitor submitted and missing ballots.
* Inspect permitted integrity information.
* Manage valid corrections or exceptional cases.
* Verify final ballot counts.

Unpublished jury allocations must remain secret.

3.3 Televoting management

Organizers must be able to:

* Configure voting rounds.
* Open, close and control voting.
* Monitor incoming votes and totals.
* Enforce voting eligibility and limitations.
* Investigate discrepancies.
* Verify that official totals originate from canonical voting records.

Unsafe direct database writers must not remain accessible.

3.4 Essential Organizer experience

Release only the workspaces required to support the enabled contest systems:

* Overview.
* Delegations / Confirmations.
* Voting / Jury.
* Voting / Televote.
* Relevant integrity and recovery controls.
* Results/publication controls only when required and certified.

Every critical action must use verified permissions, explicit edition/show context, server validation and appropriate audit/receipt mechanisms.

4. Technical work priorities

Priority 0: Production database safety

Owner: System / Supabase

This is the highest-risk release dependency.

Required work:

1. Recheck the actual current production migration and schema-effect frontier using bounded read-only inspection.
2. Distinguish migration-history differences from genuinely missing database effects.
3. Verify the existing source-defined local beta baseline.
4. Complete and rehearse necessary forward-only recovery changes on isolated infrastructure.
5. Verify canonical database writers, grants, RLS and protected commands.
6. Prepare production migration approval, backups, restoration and rollback procedures.
7. Obtain explicit authorization before any hosted database changes.

The merged S02 baseline in PR #2446 is useful progress, but does not establish production equivalence.

No broad migration replay, history rewriting or unverified SQL application is permitted.

Priority 1: Complete voting safety

Owner: System / Voting

Immediate focus:

* Select and integrate one safe S08 solution from PR #2447 and PR #2448, avoiding duplicate implementations.
* Remove unsafe Organizer televote direct-write paths.
* Ensure stale or cross-edition voting contexts fail closed.
* Verify jury ballot secrecy.
* Verify round status and deadline enforcement.
* Verify ballot uniqueness, idempotency, retries and receipts.
* Verify correct vote aggregation.
* Protect unpublished results.

Resolve the root cause of voting failures rather than merely making individual tests pass.

Priority 2: Complete essential Organizer workflows

Owner: Organizer

Prioritize:

* Confirmation management and reviews, including the remaining work in PR #2283.
* Jury voting administration.
* Televoting administration.
* Current edition/show context safety.
* Error, retry and recovery states.

Avoid spending this release period on unrelated Organizer dashboards or cosmetic redesigns.

Priority 3: Prepare the public application

Owner: Public / Navigation

Complete and verify:

* Home.
* Authentication and session transitions.
* Participate.
* Confirmation UI.
* Jury UI.
* Televoting UI.
* Minimal Explore, Results and Me surfaces.
* Feature rollout and route restrictions.

The installed PWA, mobile browser and desktop website must support their intended launch workflows safely.

Preserve the existing V3 visual design, floating bottom navigation, protected mobile top safe zone and accessible controls.

Do not undertake another complete visual redesign.

Priority 4: Build the soft-launch feature gate

Owner: System / Public / Release Integrator

Introduce or adapt the existing rollout infrastructure to support:

State	Behavior
Public	Available to eligible users
Testing	Available only to explicitly authorized testers
Hidden	Unavailable to ordinary users

The state must be centrally governed and server-enforced.

Hidden features must not leak through:

* Navigation.
* Search results.
* Deep links.
* API access.
* PWA shortcuts.
* Notifications.
* Direct backend mutations.

A hidden UI button is not a security boundary.

7. Launch GO/NO-GO rules

GO: All mandatory workflows and integrity requirements pass, production compatibility is verified, and the release has explicit approval.

NO-GO: Any security, voting integrity, mandatory workflow, database migration or release-certification blocker remains unresolved.

If the required public release cannot safely be completed by November 14, use that date for a controlled, clearly labeled owner-only beta or a safe read-only preview, if independently approved.

Do not enable official public voting merely to meet the date.

8. After launch

Continue development without reopening completed architecture unnecessarily.

Recommended expansion sequence:

1. Finish public country, edition, entry and artist/song experiences.
2. Complete Results, Scoreboard, Live and archival experiences.
3. Improve notifications, account features and participant history.
4. Release Fantasy, Predictions and fan-engagement features.
5. Expand advanced analysis and historical tools.
6. Complete Terra Solaris World and institutional governance.
7. Finish remaining Organizer functionality and full V3 certification.

Each feature must have its own implementation, testing, rollout and verification evidence.

9. Final launch definition

Solaris Studio V3 Soft Launch is ready when users can reliably perform the core contest actions, organizers can safely control those actions, and the released application is coherent, secure and usable.

Full V3 feature completeness is not required on November 14.

Official contest integrity is.

Target: 14 November 2026.

Release strategy: Small, functional, polished, verified and progressively expandable.
