# Solaris Studio App V3
## Complete Product, UX, Visual Design, Interaction, Architecture, Migration & Release Specification

This is the version I would now treat as the **canonical V3 blueprint**.

It incorporates the whole discussion, including the later critical review. So this is **not** merely the prettiest version of the earlier concept. It deliberately fixes the weak spots we identified: over-dynamic Home layouts, overly linear contest-state thinking, ambiguous MySolaris/Me ownership, possible overuse of glass and motion, optional-versus-required task confusion, multi-device conflicts, spoiler handling, organizer context safety, stale-state recovery, notification fatigue, production egress risk, and the danger of V3 becoming an enormous rewrite.

The intended result is very specific:

> **Solaris Studio V3 should feel like an entirely new premium app, while retaining the trustworthy backend, data, workflows and integrity contracts that already work.**

The old and new apps should look like different generations.

But a returning user should still think:

> “Everything I need is still here. It just suddenly makes much more sense.”

And, preferably a few seconds earlier:

> “Holy shit, this looks expensive.”

A demanding target, but apparently we have chosen software instead of a peaceful hobby.

---

# Part I
# Product definition

## 1. What Solaris Studio V3 is

Solaris Studio V3 is the **digital operating system of the Solaris Song Contest**.

It is not primarily:

- an archive website
- a results database
- an admin dashboard
- a voting site
- a collection of contest forms

Those remain capabilities.

The product itself understands four things:

### What is happening?
Canonical contest and workflow state.

### Where is this user in that world?
Role, delegation, edition membership and participation state.

### What should this user do?
Actions and responsibilities.

### What deserves this user’s attention?
Urgency, importance and delivery policy.

The interface is the projection of those answers.

---

# 2. The V3 product promise

The app must reliably answer:

> **What matters to me right now?**

without requiring users to understand Solaris Studio's internal information architecture.

The user should not need to know that “jury submissions” happen to live three routes beneath a show entity.

If Solaris knows the user needs to submit a jury ballot, Solaris should surface:

> **Jury voting · 8/15 complete · closes in 3h**

and take them directly there.

---

# 3. What must remain from the existing Solaris

V3 is **not a backend rewrite**.

Several current concepts are already correct and should be evolved rather than discarded.

The current product already has five stable global areas:

**Home · Explore · Participate · Results · Me**. 

The current Participate implementation already has a meaningful task model with attention-required tasks, upcoming tasks, completed tasks, deadlines, countdowns and explanation text. 

The current Organizer Home already follows a good exception-first pattern through “Do now”, Inbox, Upcoming and edition readiness. 

The current app also already contains notification, personal-attention and participation machinery that V3 can consolidate instead of duplicating.  

Therefore the V3 rule is:

> **Preserve correct domain behaviour. Replace fragmented presentation and duplicated client reasoning.**

# Part II
# Core product principles

## 4. Principle 1: internally sophisticated, externally simple

V3 may contain:

- State projections
- Journey computation
- Action generation
- Attention policies
- notification scheduling
- capability resolution
- conflict detection
- cache reconciliation

Users should not feel any of that machinery.

They should feel:

> “Solaris understands my situation.”

---

# 5. Principle 2: action before navigation

Bad:

> Home → Participate → Jury → Semi-final → ballot → continue

Preferred:

> **Jury voting closes in 3h → Continue**

Navigation still exists for discovery.

Actions bypass unnecessary navigation.

---

# 6. Principle 3: stable structure, dynamic emphasis

This corrects one weakness in the earlier concept.

Home should react to:

- urgent deadlines
- show day
- live broadcasts
- voting
- published results

but should **not completely rearrange itself every few hours**.

The user must maintain spatial memory.

Canonical Home order remains:

**Context → Now → Current Contest → Coming Up → Latest**

What changes is **importance and scale**, not the mental model.

---

# 7. Principle 4: required, optional and urgent are different things

These must never be conflated.

A jury ballot can be:

**required but not urgent**

A public televote can be:

**urgent but optional**

An integrity problem can be:

**important without a deadline**

Therefore V3 stores these concepts separately.

---

# 8. Principle 5: one canonical truth

There must not be separate authoritative truth for:

- Journey
- Home
- Participate
- notifications
- Organizer

Canonical domain state is authoritative.

Everything else is derived.

```text
Canonical domain state
        ↓
Experience projections
        ↓
Home / Journey / Actions / Attention / Organizer / Notifications
```

---

# 9. Principle 6: beauty is functional

Aesthetic ambition is not optional.

V3 should be substantially prettier than current Solaris.

But visual intensity must communicate hierarchy.

Quiet screens remain restrained.

High-impact moments become expressive.

If every screen glows, blurs, pulses and expands, the app stops looking premium and starts looking radioactive.

> Participate

for personal contest activity.

That is three doors into one hallway.

# Part XVIII
# Organizer risk model

## 80. Risk Tier 1

Low risk, reversible.

Examples:

- edit copy
- modify draft schedule

Normal save.

---

# 81. Risk Tier 2

Operational.

Examples:

- open confirmation
- send reminder
- start jury window

Review sheet.

---

# 82. Risk Tier 3

High consequence.

Examples:

- close voting
- publish results
- disqualify entry
- reopen finalized process

Explicit consequence confirmation.

---

# 83. Risk Tier 4

Critical platform operation.

Examples:

- delete edition
- override official finalized result
- platform-wide emergency mode

Require stronger confirmation, possibly reauthentication.

Potential future dual approval.

---

# 84. Safe undo

For safe reversible actions prefer:

> Announcement archived  
> **Undo**

instead of endless confirmation dialogs.

# The intended final feeling

A V3 user should not experience:

> “Solaris has 140 features.”

They should experience:

> **“Solaris always seems to know what I need.”**

A fan should be able to open the app and immediately understand what is happening.

A delegation manager should instantly know what remains unfinished.

An organizer should see the problem that needs intervention before searching for it.

A results nerd can still disappear into voting relationships for three hours if they so desire. We should not deny anyone their particular form of entertainment.

And aesthetically, the old and new systems should not merely differ in polish.

They should differ in **generation**.

Current Solaris:

> capable web product adapted into an app.

Solaris Studio V3:

> **a purpose-built, premium contest operating system with cinematic event moments, restrained everyday UI, strong editorial identity, tactile interactions and an architecture that actually understands the competition it is presenting.**

That is the V3 I would now consider worthy of implementation.
