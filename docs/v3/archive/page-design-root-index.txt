SOLARIS STUDIO V3

UNIVERSAL VISUAL REDESIGN & THREE-EXPERIENCE COMPLETION PLAN

Status: implementation specification, not a completion certificate
Scope: public directory roots, relevant entity/detail pages, and visual consistency of the five principal public product areas
Authority: supplements the existing canonical V3 Three-Experience Design Manifesto, updated Public Product/Design/Navigation Master Plan, safe-zone and bottom-navigation specifications, and System/publication/release contracts. It does not override them.

1. Why the existing implementation is not acceptable

The three supplied installed-iPhone screenshots expose the gap:

• Countries: relatively compact, engaging flag grid, but the two collection buttons do not clearly distinguish the selected scope. The underlying code defaults to All countries, so 67 matching may be correct; this is first an active-state clarity failure, not proof of a wrong query. The opening introduction and control stack are also taller than necessary.
• Editions: different, display-like headline typography; a large search/filter stack; the current-edition card is disproportionately tall; past entries feel like an unrelated layout and lose browsing density.
• Tools: headline treatment differs from Countries; full-width filter control feels excessive; “Browse” followed by “Follow the contest” creates two weak heading levels; long boxed rows resemble a settings page instead of useful tool discovery.
• All three: common dark background and floating dock exist, but they do not share a coherent information rhythm. The dock visually overlaps list content in the captured scroll positions; verify the final item is actually scrollable above it and never treat a screenshot alone as proof that content is inaccessible.

Root cause to correct: common color and shell do not equal common design language. The actual code has a specialized Countries screen, separate Editions composition and the generic V3DirectoryFamilyIndex for Tools/Site Directory. The generic component must be improved without forcing all domains into the same card/list layout.

2. Exact product contract

Solaris is one product, one canonical backend, three deliberately different presentations:

1. Installed PWA: canonical AppShell, compact app toolbar, touch-first focused collections, sheets, native-feeling back/drill-down, existing five-tab floating Liquid Glass navigation. No mobile-web masthead or website footer.
2. Mobile browser: compact editorial website header, browser-native breadcrumbs, full-width readable rows or content-specific grids, conventional links/history, no installed floating dock by default. Never switch to app mode because the viewport is narrow.
3. Desktop/browser: existing desktop shell, visible IA, contextual filter rail when helpful, higher information density, wider editorial layouts and keyboard/mouse utility. Installed tablets stay in the installed-app family; tablet browsers stay web.

All three share canonical queries, server-owned feature flags, authorization, state, IDs, publication rules and URLs. No three full hidden trees, no duplicate fetches, no device-specific business logic.

3. The unified visual grammar

These are proposed implementation targets, to be reconciled with existing Solaris tokens and approved screenshots, not claims that they are already canonical CSS values.

3.1 Typography and hierarchy

• Body/UI font: existing standard Solaris interface typeface. Stop using decorative/block display lettering for ordinary directory titles; reserve expressive display type for approved contest artwork and major editorial moments only.
• Installed directory heading: approximately 30–34 CSS px, 700–780 weight, tight but readable line-height. Country, Edition, Tools, Archive and Rulebook titles must visually be siblings.
• Mobile-web masthead: approximately 28–32 px; compact eyebrow and at most one short explanatory sentence. Ordinary page titles should not wrap into unnecessarily tall two/three-line banners.
• Desktop masthead: approximately 36–44 px depending on page importance; editorial, not gigantic.
• Section heading: 19–23 px with one semantic heading, not stacked “Browse” + another heading unless an eyebrow genuinely adds context.
• Collection row title: 15–17 px; metadata 12–14 px with adequate contrast; status chips consistent across domains.
• Numbers/counters: tabular numerals. Scope labels and results must match actual currently selected filters.

3.2 Spacing and sizing

• Reuse one 4/8/12/16/24/32 px spacing scale. No arbitrary per-page gaps.
• Default installed-phone horizontal page inset roughly 16–20 px; mobile web about 16–20 px; desktop main content constrained to appropriate readable widths.
• Search controls approximately 46–50 px high and the same perceived height, icon size, border, radius, placeholder style and focus ring across directories within each experience.
• Category controls at least 44 px practical tap height; compact when only one filter is present; sheets for app, select/pills for mobile web, persistent rail for suitable desktop directories.
• Use consistent card corner families: small for chips, medium for rows, larger only for genuinely emphasized objects. Avoid giant boxes wrapping ordinary lists.
• A directory masthead + controls should expose actual content promptly on a standard installed iPhone. Shorten generic descriptions instead of stacking three introductory text blocks.

3.3 Surfaces and color

• Level 0: quiet dark/light canvas and subtle contextual ambience.
• Level 1: default text, flat lists, thin separators, flags, thumbnails and metadata. Prefer whitespace over another rounded card.
• Level 2: selective featured edition, live show, major story, receipt or exceptional state.
• Level 3: glass primarily in app navigation, transient controls and selected UI where approved, never coating each ordinary item.
• One set of semantic colors for primary, accent, muted text, surface, border, selected/pressed, live, upcoming, completed, locked, unpublished and error. Do not use decorative accents to suggest a false data state.
• 3:2 flags remain canonical. Missing media must use designed neutral placeholders, not invented photos/cover art.

3.4 Interactions, filters and state

• One shared accessible search contract: label, clear control, keyboard action, normalization, URL query behavior where relevant, loading/result/empty/retry.
• One consistent filter taxonomy: collection scope (e.g. SSC 22 vs All), facet (region, period, type), query. Distinguish these visually and semantically.
• An active collection choice must be unmistakable without relying on color alone: selected fill, border, check/mark if appropriate, aria-pressed, and matching results label.
• Count labels distinguish total published, matches after filters and currently displayed items. Example: “67 countries” and “Showing 24 of 67,” not an ambiguous isolated “67 matching.”
• Never assume a fixed list of available categories if its public data can change. Clear/reset restores coherent default scope and URL.
• Provide loading skeleton, genuine empty state, no-search-results state, failure + retry, feature-disabled/locked state, published-content-only behavior and long/missing-content handling for each directory.

3.5 Global safe zones and navigation

• Keep top OS safe-zone protection in the shared shell, not a bespoke padding-top per page. No meaningful text, buttons or icon controls behind status bar/Dynamic Island/browser chrome.
• Keep existing Liquid Glass tab bar geometry, behavior, selected lens and five canonical destinations owned by Navigation lane.
• In installed-app mode, shell-owned scroll padding must account for dock height + floating gap + bottom safe area + comfortable margin, including final item, sheet controls, keyboard and focus scrolling. Do not pad every card individually.
• The mobile browser gets its own header and browser-navigation conventions; no floating installed-app dock. Desktop gets its own global navigation. Avoid duplicate shell renderers.

4. Shared implementation architecture

Use existing ownership, do not create competing frameworks:

• Runtime decision stays with useV3DirectoryPresentation / established Country runtime hook and AppShell platform resolution. Viewport only selects layout within the web family, never installed status.
• Share semantic collection logic, not entire incompatible page compositions: DirectoryTitle, DirectorySearch, CollectionScope, FacetControl, ResultCount, SectionHeading, ItemStatus, DirectoryEmpty/Error, DirectoryItemLink.
• Introduce domain composition slots/variants for V3DirectoryFamilyIndex where appropriate: flag-grid, chronology, broadcast-list, editorial-story, reference-index, rulebook-outline, music-catalogue, action-directory, sitemap.
• Preserve a single source query/model per route and transform once to a common semantic view-model. Branch only the visible presentation between installed/mobile-web/desktop; do not mount all modes invisibly.
• Use scoped design tokens and CSS; consolidate existing v3-directory-family.css and specialized directory files by design responsibility without erasing genuine domain differentiation. No uncontrolled global !important overrides.
• Do not rewrite working shells, Supabase RLS or navigation ownership to fix ordinary spacing.
• Keep bundles lazy and the fixed 1,800 KiB combined JS+CSS gzip budget. Aim for at least 30 KiB buffer on the integrated release build, subject to evidence, rather than a brittle 1 KiB pass. Use exact-head reports.

5. Root-by-root redesign: 12 routes

Each route below has three separate visual acceptance targets. Data/permissions remain identical.

5.1 /countries — Countries discovery

Region displayed consistently; long names wrap/ellipsize intentionally. Current movement (debuts/withdrawals) becomes a bounded secondary section rather than competing with browse.

Mobile web: Editorial Countries heading, brief current-edition context, a compact scope selector, search and native region filter; readable flag-led rows with region and optional published status. No forced two-column grid on very narrow browser widths.

Desktop web: Editorial intro, persistent region rail, current-edition context and responsive multi-column flag explorer; scannable states and generous whitespace.

Fix now: Ensure default participatingOnly=false looks like All selected; check both click actions and displayed 34/67 totals against the same published view. Verify no mismatched count when search or region changes. Avoid replacing currently correct flag discovery.

5.2 /editions — Contest chronology

Installed PWA: Replace the inconsistent display-font heading with the shared directory heading. One compact featured SSC 22 block containing state, host, next event (if public), and a single action; move status and any unavailable winner explanation to subdued metadata. List past editions as compact, browsable timeline rows, not oversized individual slabs.

Mobile web: Small editorial masthead, one featured current edition, chronological list showing edition, published host/year/state and winner only when public; native year/status filter.

Desktop web: Wider chronology with an edition-artwork feature when available, filter rail (year/era/status), a well-spaced 2-column timeline/card grid, and clear lifecycle changes.

7. Consistency review of the five product roots

The directory pass must not make the rest of V3 feel like a different product:

• Home: canonical Context → Now → Current Contest → Coming Up → Latest; one primary action, at most two secondary actions, bounded summaries. Do not convert it into a discovery feed.
• Explore: one universal search and a curated Current edition → Discover → Archive → More hierarchy. Show short previews and “See all” links; not a wall of destination cards.
• Participate: responsibilities and deadlines first, optional fan activities clearly secondary; distinct workflow states and preserved command/receipt authority. Visual consistency only, not a risky workflow rewrite.
• Results: official result/story hierarchy first, data tools second; charts/tables specially designed per experience; protect spoilers and publication.
• Me: identity/current/history/activity/receipts/following/preferences/account with compact coherent sections; don’t copy critical tasks out of Participate.

Apply the same standard to global search, notification centre/settings, auth, launch, offline, error/retry and maintenance. Organizer follows the same token and runtime principle, but remains a separately owned operational-design lane with stronger data density and no unilateral shared-shell rewrites.

Representative environments: installed 320/390/430-width phone, installed tablet; browser 320/390/430 phone; tablet browser portrait+landscape; narrowed desktop web; 1440px and 1920px desktop; light/dark if supported; 200% text/zoom, keyboard, reduced motion/transparency. Real tests required:

• Real rendered screenshots and visual comparison for each required route/experience; three CSS classes are not evidence of quality.
• CI uses isolated local or disposable Supabase only, fails closed when unavailable and never connects tests to production.
• Combined JS+CSS gzip remains <=1,800 KiB, with independent exact-head budget and browser evidence; no artificial exemptions or lazy-route defeats.

10. Page-by-page acceptance rubric

A page is not complete until every item is true:

1. Identity: purpose and domain priority immediately obvious, within one screen.
2. Family resemblance: heading, search, filter, status, spacing and control language recognizably consistent with other V3 directories.
3. Domain difference: Countries still feel geographic, Editions historical, Shows broadcast-led, Stories editorial, Reference encyclopedic, Music music-first, Rules official and Tools action-focused.
4. Three true experiences: installed app, mobile browser and desktop are deliberately different and actually rendered, not hidden copies.
5. Truth: official counts, permissions, links, spoiler rules and publication states are backed by canonical sources.
6. Usability: actions, last content, search and deep links remain reachable with keyboard/touch, safe zones and zoom.
7. Evidence: exact-head Quality + Browser Audit + bundle checks pass, screenshots reviewed, accessibility evidence attached and registry status truthful.

Explicit rejection criteria

Reject a page that has any of: decorative block-font headings in routine directories; a new arbitrary search/filter geometry; giant empty hero cards; nested card-in-card rows; a generic one-size-fits-all item layout; visually misleading active filter; duplicate mobile navigation; dock-occluded final items; invented historical/media data; screenshot-only fixes that break other experiences; or an unpaginated list advertised as a complete catalogue.

Final outcome: One Solaris Studio. One authoritative backend. One visual design system with page-specific identity. Three genuinely native-to-context frontend experiences. Every directory and related detail page tested and visually certified, rather than simply merged.
