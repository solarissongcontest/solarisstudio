# SOLARIS STUDIO V3  
# PUBLIC PRODUCT, DESIGN & NAVIGATION COMPLETION MASTER PLAN

## Consolidated canonical redesign plan for Public / Participant / Fan V3

---

# 0. STATUS AND AUTHORITY OF THIS DOCUMENT

This document consolidates and extends the existing Solaris Studio V3 Public design requirements into one implementation-ready product and visual completion plan.

It is intended to close the gap between:

- technically migrated V3 routes;
- canonical Public capability implementation;
- genuine V3 information architecture;
- visual/product parity;
- responsive quality;
- the intended iPhone-first navigation experience;
- final release certification.

The existing canonical V3 plans remain authoritative for:

- domain ownership;
- database truth;
- authorization;
- operations;
- receipts;
- publication;
- privacy;
- security;
- production isolation;
- migration safety;
- Organizer responsibilities;
- system reliability.

This document is specifically authoritative for the consolidated **Public product structure, layouts, visual composition, navigation behaviour, entity presentation, responsive design and product-parity acceptance** described below.

Where visual ambitions conflict with security, accessibility, canonical state, data integrity or production safety, those requirements win.

The canonical Public top-level areas remain:

**Home · Explore · Participate · Results · Me**

This distinction is final.

---

# PART I  
# THE ACTUAL V3 PRODUCT STANDARD

## 1. V3 is not a reskin

A route is not V3 merely because it has:

- the V3 background;
- new typography;
- rounded corners;
- Liquid Glass controls;
- a new header;
- blue gradients;
- the V3 tab bar.

A screen fails V3 product acceptance if it preserves the same:

- layout;
- list hierarchy;
- composition;
- information density;
- interaction model

while merely changing presentation.

The mandatory review question is:

> **If all V3 colours and surface styling were removed, would this still obviously be the old Solaris screen?**

If yes, redesign it.

---

# 2. Product parity is separate from technical migration

The current project must stop allowing one word such as `cutover` to imply all of:

- route migrated;
- backend migrated;
- frontend integrated;
- legacy removed;
- visually redesigned;
- responsive;
- accessible;
- release-certified.

These are different facts.

Every Public capability should expose at least four dimensions:

### A. Capability migration

Examples:

- missing
- mapped
- building
- implemented
- integrated
- cutover
- retired
- merged

### B. Product parity

Recommended states:

- `unaudited`
- `legacy`
- `partial`
- `parity`

### C. Verification

Examples:

- untested
- component-tested
- workflow-tested
- responsive-tested
- visual-tested

### D. Certification

- uncertified
- candidate-certified
- released

Example:

> **Edition**  
> Backend/capability: cut over  
> Product parity: partial  
> Responsive: tested  
> Certification: not certified

A technically migrated route must never be presented as complete V3 while its visual/product experience remains legacy.

The canonical capability model already distinguishes implementation, parity, cutover and certification.

---

# 3. Public V3 design character

Solaris V3 should feel:

- editorial rather than administrative;
- calm rather than card-heavy;
- information-rich without becoming dense;
- premium without coating everything in glass;
- app-like rather than website-like on phone;
- expressive at important moments;
- restrained during ordinary browsing;
- clearly structured before decoration is added.

High-impact moments may become expressive.

Routine content should remain quiet.

If every section glows, blurs, floats and animates, hierarchy disappears.

Liquid Glass belongs primarily to the **control/navigation layer**, not the content layer. The canonical source already requires normal content to remain mainly flat.

Apple similarly positions Liquid Glass as a distinct functional layer for controls/navigation rather than something to put throughout ordinary content.

---

# PART II  
# DESIGN SYSTEM AND LAYOUT FOUNDATIONS

## 4. Content surface hierarchy

Public V3 should use four major surface classes.

### Level 0: Background

The application canvas.

May contain:

- subtle edition tint;
- very restrained depth;
- background extension beneath floating controls;
- artwork-derived ambience on appropriate entity pages.

It must not compete with content.

### Level 1: Content

Primary page content should largely be flat.

Examples:

- text;
- lists;
- ranking rows;
- story previews;
- song rows;
- timelines;
- metadata;
- section groupings.

Do not wrap every section in a floating card.

### Level 2: Emphasized content

Use cards selectively for genuinely bounded objects such as:

- a current-edition hero;
- urgent responsibility;
- live show status;
- result winner;
- receipt;
- media player;
- significant empty/error state.

### Level 3: Control material

This is where Liquid Glass belongs:

- bottom navigation;
- floating controls;
- compact tool groups;
- segmented controls;
- transient sheets;
- selected navigation lens;
- selected sliders/toggles where appropriate.

---

# 5. Kill over-cardification

A recurring V3 anti-pattern has been:

> outer rounded card  
> → inner rounded card  
> → rounded search field  
> → rounded icon container  
> → rounded button

This must stop.

Use:

- spacing;
- typography;
- separators;
- hierarchy;
- alignment;
- background transitions

before adding another box.

Rules already explicitly require one visually clear search surface rather than card-within-card search composition.

Apply the same principle throughout Public V3.

---

# 6. Root-page content budget

Root and Overview screens summarize.

Dedicated collection screens contain the full dataset.

Never dump:

- all countries;
- all participants;
- all songs;
- all shows;
- all stories;
- every analysis tool

onto a root page merely because the projection returned them.

General principle:

> **Overview tells me what matters.  
> Collection lets me explore everything.**

---

# 7. Phone-first design

Public V3 is designed around approximately the **390×844 iPhone class** first, while also validating smaller and larger phones.

Every design must then adapt to:

- small phone;
- standard phone;
- large phone;
- tablet portrait;
- tablet landscape;
- desktop;
- wide desktop.

Mobile must never contain:

- compressed desktop tables;
- tiny controls;
- unreachable floating actions;
- navigation obstruction;
- top-chrome obstruction;
- drag-only functionality;
- endless Overview pages.

Desktop is the same product, not an unrelated admin-style web version.

A reasonable desktop composition is:

**Navigation / sidebar · Main content · Optional contextual panel**

without changing the conceptual IA.

# PART III  
# GLOBAL PUBLIC SHELL

## 8. Top chrome

The current V3 top area must become less vertically expensive.

### Mobile target

The top chrome should normally communicate only:

- current context where necessary;
- page title where necessary;
- one or two meaningful global actions;
- temporary state such as Live.

Avoid simultaneously stacking:

- giant edition label;
- giant title;
- subtitle;
- context line;
- giant action row;
- another section header.

### Behaviour

On scrolling:

- page content must gain visual priority;
- the chrome may condense where appropriate;
- content must never disappear underneath it;
- safe-area spacing remains correct;
- sticky elements must not stack into a giant obstruction.

The known visual audit specifically flags top chrome as too vertically expensive.

---

# 9. Global transitions

Route changes should feel continuous but not theatrical.

Use:

- short crossfade/translation for hierarchy changes;
- directional motion for push/pop;
- direct manipulation for tab swipe;
- immediate acknowledgement;
- skeletons only when necessary.

Avoid:

- fullscreen fade to blank;
- repeated splash screens;
- long hero animations on routine navigation;
- transition animations that block input.

Major motion should target approximately 60 fps and tab acknowledgement under ~100 ms.

# PART IV  
# THE NEW BOTTOM NAVIGATION SYSTEM

## 10. Bottom navigation is a release-critical V3 system

The bottom navigation is no longer “verify only.”

It is a canonical product requirement.

The exact public destinations remain:

1. Home
2. Explore
3. Participate
4. Results
5. Me

The visual target remains:

> **current Instagram iPhone floating navigation geometry**  
> + **Solaris destinations and icons**  
> + **a slightly more Apple-like Liquid Glass interpretation**.

But the interaction target is now clarified further using the discussed Liquid Glass references.

---

# 11. Navigation visual target

At first glance the bar should look like a modern iPhone floating tab bar, not:

- a generic frosted card;
- a website navigation pill;
- five buttons inside a glass rectangle;
- an oversized dock.

Required matching dimensions include:

- shell silhouette;
- pill geometry;
- horizontal inset;
- vertical placement;
- safe-area relationship;
- expanded height;
- compact height;
- icon centre positions;
- icon optical size;
- selected lens dimensions;
- lens radius;
- lens relation to shell;
- visual density;
- shadow extent.

Freeze the approved Instagram reference before final geometry tuning.

Create measured reference tokens:

- shellWidth
- shellMaxWidth
- shellHeightExpanded
- shellHeightCompact
- horizontalInset
- bottomInset
- shellRadius
- slotWidth
- iconOpticalSize
- iconCenterX[]
- lensWidth
- lensHeight
- lensRadius
- lensOvershootMax
- compactWidth
- compactHeight
- shadowSpreadBudget

Do not call N0 complete without a real approved reference package.

---

# 12. Quiet shell, expressive lens

The outer shell should remain relatively calm.

Most of the physical Liquid Glass personality belongs to the **selected lens**.

The shell provides:

- a subtle transparent material;
- separation from content;
- restrained highlight;
- background blur;
- safe icon legibility.

The selected lens provides:

- refraction;
- specular rim;
- subtle chromatic edge;
- physical deformation;
- long-press expansion;
- drag/stretch behaviour;
- spring settlement.

Do not make the entire bar behave like jelly.

---

# 13. Normal tap

Normal navigation remains immediate.

Sequence:

**tap destination**  
→ immediate tactile/visual acknowledgement  
→ lens begins moving  
→ route changes  
→ lens settles on selected icon

A normal tap does not require long press.

Selecting the active root tab should preserve the existing expected behaviour such as returning toward the root/top.

---

# 14. Long-press lens activation

This is now a first-class interaction requirement.

When the currently selected lens is held:

### Phase A: touch down

Immediately:

- slight lens compression;
- tiny specular change;
- subtle haptic where supported.

### Phase B: long-press threshold

After approximately 250–350 ms, tuned on device:

- lens expands;
- refraction strengthens;
- radius becomes softer/more liquid;
- specular highlight intensifies slightly;
- the object feels “picked up”;
- second subtle haptic confirms engagement.

The exact scale should be measured visually, likely in approximately the 1.3–1.45× family rather than blindly copying a demo.

Apple's custom Liquid Glass controls explicitly support interactive scaling, bouncing and shimmering responses.

---

# 15. Dragging the engaged lens

While held:

- lens centre follows finger directly;
- no spring runs while finger owns the object;
- leading edge stretches in drag direction;
- trailing edge lags subtly;
- visual deformation is velocity-aware;
- icon emphasis interpolates continuously;
- crossing a destination centre may generate a light haptic;
- hit geometry remains stable;
- edge movement uses nonlinear resistance.

At Home/Me boundaries:

- outward motion is resisted;
- small bounded overshoot is allowed;
- nonexistent destinations are never exposed.

The existing canonical specification already requires pointer following, directional stretch, icon interpolation and edge resistance.

An open-source implementation now used as a technical reference demonstrates press-and-hold bubble morph, drag-to-switch and momentum deformation with spring physics.

---

# 16. Lens optics

The lens should be actual refractive glass rather than merely another translucent gradient.

Preferred architecture:

**Lens geometry**  
→ displacement field  
→ SVG `feDisplacementMap` / equivalent renderer  
→ actual apparent pixel bending  
→ restrained chromatic edge  
→ specular highlight  
→ tint/blur  
→ fallback material

Aave's production web implementation demonstrates generated displacement maps and Safari-specific handling for real glass-like refraction.

Implementation requirements:

- position updates must be cheap;
- drag should use refs/CSS variables/compositor-friendly updates;
- avoid React rerender per pointer frame;
- regenerate expensive optical data only when lens geometry meaningfully changes;
- isolate filter work;
- degrade effects before degrading responsiveness;
- provide Safari/iOS-specific validation;
- provide fallback where advanced distortion is unavailable.

---

# 17. Release physics

On release:

1. measure displacement;
2. preserve velocity;
3. resolve destination;
4. settle page, lens and icon emphasis together;
5. use one interaction owner.

Fast flick:

- may commit with less travel.

Slow drag:

- requires more deliberate displacement.

Cancelled drag:

- returns to original destination;
- creates no history entry.

Committed drag:

- settles naturally;
- creates only the canonical target route;
- does not trigger a second unrelated animation.

---

# 18. Whole-page top-level swipe

The final Public V3 must support:

**horizontal finger drag**  
→ current page follows finger  
→ adjacent page appears live  
→ lens moves with exactly the same progress  
→ icon emphasis interpolates  
→ release chooses destination  
→ page + lens settle together.

This is explicitly required by the canonical navigation specification.

The existing `V3TopLevelSwipeSurface` foundation must not count as implemented merely because the component exists.

It becomes implemented only when:

- the real shell mounts it;
- real route owners provide safe previous/current/next surfaces;
- gesture ownership works;
- route memory survives;
- no duplicate data subscriptions appear;
- accessibility isolation works;
- actual device interaction passes.

---

# 19. Gesture arbitration

Whole-page swipe must fail closed.

Vertical scrolling wins when gesture intent is vertical.

Nested horizontal content wins for:

- scorecharts;
- tables;
- media rails;
- carousels;
- sliders;
- chip rails;
- sortable rows;
- charts.

Global swipe is disabled around:

- critical forms;
- active submission workflows;
- modal/sheet ownership;
- iOS edge-back gestures;
- keyboard-sensitive contexts.

Long press and drag must always have non-gesture alternatives. Long press is never essential for access.

---

# 20. Expanded and compact states

The bar supports a genuine compact/retracted morphology.

Near page top:

**expanded wins**

Sustained downward scrolling:

**compact state**

Upward intent:

**expand sooner**

Tiny scroll oscillations:

**do nothing**

Compact mode must not simply use:

`transform: scale(...)`

if that shrinks touch targets or changes proportions incorrectly.

Compact mode must preserve:

- selected state readability;
- touch targets;
- material quality;
- safe area;
- proper icon placement.

# PART V  
# HOME

## 21. Home's purpose

Home answers:

> **What matters to me right now?**

It is personal and operational.

It must not become:

- a discovery feed;
- an archive;
- an everything dashboard;
- a giant task list.

Its permanent skeleton remains:

1. Context
2. Now
3. Current Contest
4. Coming Up
5. Latest

Optional personalization may follow.

---

# 22. Home content budget

Maximum normal density:

| Content | Maximum |
|---|---:|
| Primary action | 1 |
| Secondary actions | 2 |
| Current contest hero | 1 |
| Upcoming | 3 |
| Latest | 3 |
| Secondary personalization | 1 |

Overflow links into the correct destination.

Do not turn Home into Dashboard 2.

---

# 23. Home state system

Home must be visually stable while changing priority.

### Calm

- greeting/context;
- all caught up;
- current edition;
- next event;
- recent updates.

### Action required

One major responsibility becomes primary.

Example hierarchy:

**1 thing needs your attention**  
Jury voting  
8/15 complete  
deadline  
**Continue**

Current contest remains visible underneath.

### Urgent

The same layout becomes more urgent without becoming a completely different page.

Time remaining becomes dominant.

### Show day

The upcoming show becomes the central moment.

### Live

Show state becomes dominant but does **not** automatically force Live Mode.

### Voting open

Voting CTA appears according to eligibility/state.

### Results available

Respect spoiler preference.

### Post-edition

Winner/edition completion transitions gracefully toward archive and the next edition.

# 93. Final navigation test

Someone familiar with the approved iPhone reference should first notice:

**Solaris icons**

not:

- wrong bar size;
- wrong spacing;
- wrong lens;
- wrong compact shape;
- wrong vertical placement.

During interaction they should feel:

- immediate touch response;
- convincing lens engagement;
- direct finger ownership;
- liquid deformation;
- velocity-aware release;
- synchronized page/lens movement.
