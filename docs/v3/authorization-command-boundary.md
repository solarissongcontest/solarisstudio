# Permission mutation boundary

The nine-argument `studio2_apply_permission_change_r3` is the sole public access-change command. It checks a live session and current permission capability before operation recovery, fingerprints the target, change, expiry, expected revision and immutable second-operator approval, then commits permission state, server revision, audit, approval consumption and receipt together. A lost response replays before checking consumed approval or advanced revision.

The older eight-argument R3 endpoint is inaccessible to application roles. The owner-only write implementation cannot claim another operation; it requires the processing receipt established by the reviewed command. Service credentials cannot write approval requests or operation receipts. Existing receipts from the earlier scope-only protocol can only be read back through their matching consumed approval request; changed input is rejected.

The unattached duplicate version-trigger/counter chain is removed. The actual attached subject-version trigger is bounded housekeeping, and the HOD role is a fixed consequence of the canonical country association. The remaining zero-baseline initializer is private and cannot grant access. Their S16 classification requires exact implementation fingerprints, owner, fixed search path, grants, source table/column privileges, trigger attachments and caller graph. Restoring a peer caller or raw grant invalidates that proof.

Executable proofs: `.github/tests/v3-authorization-command-boundary.sql`, `.github/tests/v3-account-session-authority.sql`, and `src/lib/v3-authorization-mechanisms.test.ts`. The SQL covers two-operator separation, current authorization, stale input, lost-response and historical readback, conflicting retry, receipt-failure rollback, version bounds, transport misuse and revoked-session denial. Clean replay and current-main upgrade must validate the final migration chain; earlier evidence is not final candidate certification.
