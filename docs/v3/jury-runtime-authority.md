# Jury command recovery and internal mechanisms

The existing `studio2_apply_jury_vote_change` and `studio2_apply_jury_ballot_review` are the mutation boundaries. Both require an active session and a fresh edition-scoped `jury.ballots.manage` capability. API service credentials cannot execute them. Raw Jury vote, ballot and revision writes remain closed, including column grants.

Manual scores retain their established complete request fingerprint and show-level database revision. A committed retry recovers before current scope, CAS or publication checks. Score replacement/deletion applies only to manual rows; it cannot delete or unlink immutable participant submissions. The command rechecks canonical roster, recipient, point scale, self-vote, DNV and protected-input state inside the transaction.

Ballot review fingerprints the normalized reason and target with the reviewed version. The receipt preserves immutable source scope and prior status; recovery remains possible after source deletion or finalization. A historic scope-only successful receipt can only be read back if its original immutable audit also proves the reason and version. It cannot execute a new historic mutation. Revoked sessions/capabilities are denied before either recovery path.

Score/review mutation, bounded revision advancement, audit and S2 receipt commit atomically. Existing review events retain stable operation identity. Task/notification reconciliation and provisional score-cache consequences are synchronous; failure rolls back the command. The Results lock is acquired before Jury score/row locks, and finalized, scheduled, public and archived inputs are guarded. These protections do not certify official Results calculation, which remains in frozen #1400 scope.

The six internal mechanisms have exact body hashes, owner/execute/search-path checks, exact caller topology, closed input tables/columns and hashed trigger definitions. The unit fixture is explicitly not release evidence. `.github/tests/v3-jury-runtime-mechanisms.sql` executes the live structural checks and semantic scenarios during both clean replay and current-main upgrade, including CAS, exact/changed retries, source disappearance, historical recovery, revocation, immutable evidence, publication/finalization, failed audit/receipt/event/projection/task consequences and duplicate event/notification protection.

The Organizer retains one actor-scoped reviewed request in session storage before sending. It cannot silently generate a new identity after a network, malformed or thrown response. Recovery re-enters the same authorized domain command. A visible recovery action survives refresh and works before a new preview. Conflicting edits are blocked until the uncertain request is resolved; only a proven noncommitting database rejection releases the retained request.

Parallel first attempts exposed a shared S2 claim race: `INSERT ON CONFLICT DO NOTHING` could wait for a successful receipt with the same operation ID and then incorrectly report a fresh claim. The S2 primitive now uses `INSERT ... RETURNING` to prove which invocation created the claim. Every other invocation recovers the existing receipt (including a pending one), without acquiring semantic mutation authority again. The two-session regression covers both competing CAS requests and identical simultaneous requests for scores and review.
